# Incident Response Reports

## What this demonstrates

Formal incident response documentation — a distinct SOC skill from the build-and-detect work in this portfolio's other five projects. Each report here follows NIST SP 800-61 (Computer Security Incident Handling Guide) structure: a timeline built from real evidence, indicators of compromise, MITRE ATT&CK mapping, a severity and escalation decision with stated reasoning, containment and remediation actions, and root cause analysis — including being explicit about what the available evidence does and doesn't support, rather than forcing a conclusion the evidence doesn't back.

Every incident in this repo is a real, hands-on exercise conducted against this lab's own infrastructure — not a hypothetical scenario written from imagination. Screenshots, log excerpts, and alert data throughout are the actual evidence generated by each exercise.

## What ties these together

Both incidents share a deliberate throughline: each one is scoped around a specific point in an attack chain rather than a full end-to-end compromise narrative. Incident-01 investigates a completed privilege-escalation action and reasons honestly about what can and can't be concluded about intent from the available evidence alone. Incident-02 investigates an anti-forensic action taken by an actor who already holds access, and documents in detail what it actually took to make that action detectable in the first place — including a real, currently open upstream Wazuh bug that had to be worked around before genuine detection was possible.

Neither report inflates its findings or forces a tidy conclusion where the evidence doesn't support one. Where root cause is genuinely unresolved, or deliberately out of scope, the report says so directly.
